# BLessCommander (nome nei documenti: Bracketeer)

Web app per un gruppo di amici che gioca a Magic: The Gathering Commander. Importa mazzi (Archidekt/Moxfield/testo) e registra le partite.
Un motore deterministico promuove, declassa o conferma la fascia (F1–F5) di ogni mazzo in base ai risultati.
Nessun backend: dati JSON in un repository GitHub privato, calcoli ufficiali nelle GitHub Actions (SPEC §6).

Nome app nel codice e nell'interfaccia: quello di `docs/progetto.json` (`appName`). Lingua di lavoro: italiano. L'utente non è esperto di GitHub: spiega in modo semplice.

## Stack e comandi

Vue 3 + Vite (`<script setup>`, JavaScript con JSDoc), Pinia, Vue Router hash, Chart.js (vue-chartjs), SCSS con design system proprio, font inclusi nel progetto, API REST di GitHub con `fetch`, Capacitor predisposto, Vitest, Playwright, @axe-core/playwright. Monorepo npm workspaces.

## Regole non negoziabili

1. **Zero interazioni durante la partita.** Tutto in lobby o in chiusura (3 tocchi). Solo il registratore gira un dado fisico. Se una funzione richiede il telefono in partita: fermati e proponi un'alternativa. → `docs/spec/00-indice.md` §1
2. **Desktop e mobile al 100%**, requisito bloccante: ogni funzione su entrambi, criteri di `docs/spec/05-ui-responsive.md` §5.3, mobile first.
3. **Dati derivati** (`derived/`) scritti solo dall'Action di ricalcolo, sempre da zero sullo storico. Solo il registratore chiude una partita (verifica sull'autore del commit). Riapertura solo all'unanimità. Motore deterministico.
4. **Design ispirato a Nalika e CoreUI ma scritto da zero**: nessun codice, CSS o asset copiato; niente Bootstrap/CoreUI.
5. **Nessun test chiama servizi esterni reali**: fixture e finta API GitHub su cartella locale (`docs/PIANO-Test.md` §1).
6. **Una funzionalità è finita** solo con test unitari e Playwright verdi sui 6 profili e revisione screenshot superata.
7. **Nessun componente o store importa codice di GitHub o Firebase**: tutto passa da `DataProvider` (SPEC §6.3). Funzioni del dispositivo solo da `web/src/platform/` (§6.9). Niente `alert`/`confirm`, niente font o librerie da CDN, routing hash.
8. **Il token GitHub** non si logga, non si mostra in chiaro, non va a domini diversi da `api.github.com`. Nessun segreto nel repository del codice (diventerà pubblico).
9. **Utenti di prova = membri finti** del repository dati di prova, mai account GitHub reali (SPEC §6.7). La modalità prova deve essere impossibile sul repository reale.
10. **Versione locale sempre funzionante**: `npm run dev` parte in demo senza configurazione. A fine voce dì all'utente cosa vedere in locale e come aprirlo dal telefono (SPEC §6.11).
11. **Prima di ogni comando che crea o modifica qualcosa su GitHub** (repository, impostazioni, visibilità, secret): spiega cosa fa e chiedi conferma. Mai chiedere o accettare token e password in chat.

## Protocollo di sessione

- **Inizio:** leggi CLAUDE.md e SOLO la sezione "Passaggio di consegne" + la riga della voce di lavoro in `docs/PIANO-Funzionalita.md`. Leggi solo i moduli di specifica e i casi di test indicati per quella voce.
- Lavori su **UNA voce del piano per sessione**. Se scopri lavoro extra, aggiungilo al piano come nuova voce invece di farlo subito.
- Leggi i file per intervalli di righe quando sono lunghi; ricerche mirate invece di aprire cartelle intere; non leggere mai `node_modules`, `dist`, `coverage`, `test-results`, `playwright-report`, lockfile.
- **Test:** esegui SEMPRE tramite il subagent `test-runner`; riesegui solo i falliti; non incollare mai log completi.
- **Screenshot:** analizzali SEMPRE tramite il subagent `ui-reviewer`, mai nella conversazione principale.
- **Esplorazioni ampie** del codice: usa il subagent `code-explorer` e fatti restituire solo il riassunto.
- **Fine:** spunta la voce, aggiorna "Passaggio di consegne" (max 15 righe), aggiungi le decisioni qui sotto, proponi il messaggio di commit, dì cosa provare a mano e di eseguire `/clear`.
- Comandi utili: `/riprendi`, `/testa <ID>`, `/revisione-ui <ID>`, `/consegna`.

## Decisioni

- Nome dell'app: BLessCommander; organizzazione e repository: `BLessCommander/blesscommander`, `-data`, `-data-test` (privati; il codice diventerà pubblico alla voce C-15).
- Font Inter e Cinzel da pacchetti npm `@fontsource/*` (inclusi nel progetto, nessun CDN).
- `docs/SPEC.md` è solo una nota: la specifica sta in `docs/spec/`.
- Screenshot di revisione in `review-screenshots/` (ignorata da Git), non in `test-results/`: quest'ultima è in `deny` e `ui-reviewer` non potrebbe leggerli.
- Nelle fixture Playwright non chiamare nulla `screen` (conflitto con i dispositivi): la fixture dei controlli automatici è `uiChecks` (auto). Il controllo §3.6 (solo hover) non è automatizzabile: resta nella revisione screenshot.
- Finta API GitHub: token `token-<login>`, avviabile con `startFakeGithub` (`tests/fake-github/server.js`); gancio `onWrite` per simulare il ricalcolo (B-07).
- Menu a scomparsa e finestre sono "ancorati" alla cronologia con `?overlay=<nome>` (`useOverlay`): il tasto indietro li chiude prima di cambiare pagina. Tema in `useThemeStore` (system/chiaro/scuro), salvato tramite `web/src/platform/`.
- Fixture `uiChecks`: il controllo finale automatico gira solo se il test è passato (i test saltati non aprono pagine).
- Livello dati: `DataProvider` in `web/src/data/`; schemi JSON in `schemas.js` validati con `ajv` 8 (non 6: npm può scegliere la 6 dall'ESLint, verificare con `npm ls ajv`). Il provider sta fuori dallo store Pinia (un proxy reattivo non regge i campi privati `#`). Utenti demo `demo-…`; un solo punto di scelta del provider: `web/src/data/index.js`.
- Ambiente scelto da `resolveEnvironment` (`web/src/config/environment-mode.js`) con `VITE_DATA_MODE`; la finta API vale solo su indirizzo locale (127.0.0.1/localhost), altrimenti demo. `dev:fake-github` (`tests/dev/fake-github-dev.js`) scrive il seed in `test-results/fake-github-dev`, porta 4500 (`FAKE_GITHUB_PORT`).
- In `vite.config.js` il percorso di base vale `/<repository>/` anche per `vite preview` (`isPreview`), altrimenti l'anteprima non trova i file. `preview.spec.js` fa build e preview e gira solo nel profilo `desktop-chrome`.
- `GitHubProvider` (`web/src/data/github-provider.js`): letture con ETag, scritture con `sha` e 3 tentativi, coda offline in `platform/storage` rilanciata con `flushQueue`; il token va solo a `api.github.com` o a un indirizzo locale (il costruttore rifiuta altro). Nei file l'`id` è il nome del file (non sta nel JSON); le fasce nei file sono `F1`–`F5`.
- Ambiente `github` (repository reale) solo con token salvato e mai insieme alla finta API; `checkRepository` rifiuta i repository con `testMode: true`. Tutti i provider passano `provider-contract.js` (UT-DATA); i test del provider usano la finta API vera, quelli del collegamento reale intercettano `api.github.com` senza chiamarlo.
- Motore fasce (`packages/tier-engine`): `recalculate(decks, games, group)` rigioca da zero le partite `ufficiale`. Il peso del tavolo usa le fasce dei mazzi a inizio partita (anche per D); i formati che non contano per le fasce non entrano né in TMV né in D. Un mazzo con D ≥ 1,8 e TMV entro il limite della fascia di arrivo + 1 sale per dominio (anche con meno di 3 vittorie veloci). Nel test del motore ogni caso usa `win()`/`game()` di `engine.test.js`.
- Action `recalc` (`data-actions/src/recalc.js`): funzione pura su file di testo + autori; `unknownAuthor` `deny` nell'Action vera, `allow` nelle prove locali. `derived/` si riscrive sempre per intero (i file non più prodotti si cancellano). L'Action pubblicata è un unico `engine/recalc.mjs` (esbuild), senza `npm install`.
- Dati nelle pagine (B-11): `useDataStore` espone `pendingWrites`, `dropped`, `refreshing` (= `snapshot.pending`) e `write()`; calcoli di dashboard e mazzi in `web/src/domain/snapshot-stats.js`. "Agisci come" vale solo se il repository ha `testMode` e chi accede è in `testOperators` (controllo nel `GitHubProvider`); ogni scrittura porta `actingAs`.
- Test Vitest: `vitest.config.js` inietta `__APP_NAME__`, `__ORG__`, `__DATA_REPO__`, `__TEST_REPO__` come `web/vite.config.js`. Gli screenshot a pagina intera mostrano la barra in basso a metà pagina: è un artefatto, non un difetto.
- Menu a scomparsa (B-12): geometria coperta da un test (cassetto da bordo a bordo, maschera sopra la barra in basso); il padding per il notch vale `env(safe-area-inset-*)` e non è simulabile nei browser di prova.
- Accesso (C-03): pagina `/accesso` (non nei menu), logica in `web/src/domain/session.js` (`signIn` salva il token solo se `checkRepository` è ok, poi riavvia; `signOut` lo cancella). Il not-member si riconosce da `DataError.details.reason`, non dal testo; `getCurrentUser` dà `forbidden` se `members.json` non si vede (motivo `no-access`). Nei test Playwright non usare `check({ force: true })` dove la barra in basso può coprire il punto.
- Membri (C-04): pagina `/gruppo` (`GroupView.vue`); il `DataProvider` ha `getMembers`/`saveMember`/`removeMember`, regole comuni in `web/src/data/members-rules.js` (login GitHub valido, almeno un admin). L'Action `recalc` ignora anche un elenco membri senza admin. Pulsanti: `.btn` (principale), `.btn--secondary`, `.btn--danger`.
- Modalità prova (C-04b): `actingAsOptions()` del provider restituisce anche `testMode` (vero per qualunque membro di un repository di prova); `AppLayout.vue` mostra allora il banner rosso "MODALITÀ PROVA" al posto dell'etichetta ambiente (`data-testid="test-banner"`).
- Repository di prova (C-04b2): casella nella pagina Accesso → `signIn(token, { testRepo })`; `checkRepository` pretende `testMode` con `testRepo` e lo rifiuta senza (motivi `not-test-repo` / `test-mode`). Flag in `platform/secure-storage` (`readTestRepoFlag`), `ENVIRONMENT.testRepo` e `LINKED_REPO` scelgono il repository. Dati iniziali: `npm run build:data-repo:test` (operatore = `ownerLogin` di `docs/progetto.json`, 4 utenti `test-`).
- Notifiche (C-04c): pagina `/notifiche` (non nei menu) e campanella in `AppHeader`; notifiche in `derived/notifications/<login>.json` (Action), stato letto/risposte in `users/<login>/notifications.json` (SPEC §6.4b). Pausa in partita: `notificationsPaused` in `useDataStore` (lobby/in_corso). In Playwright i 404 sui file delle notifiche sono previsti (`allowedFailures` di default, anche per la console).
- Import da testo (C-05): `parseDeckText` (`web/src/domain/deck-parser.js`) legge Archidekt/Moxfield/semplice; sideboard e maybeboard restano fuori dal mazzo. Comandanti multipli (partner, background): il mazzo ha un elenco, scelti con il pulsante "Comandante" o doppio click (solo desktop; sul telefono il doppio tocco fa zoom). Scryfall solo da `web/src/platform/scryfall.js`; il flag game changer si legge dal campo `game_changer` della carta. È sempre quella vera (anche in demo, serve internet); i test la intercettano con `tests/fixtures/scryfall-fake.js` (`mockScryfall` per Playwright, `fakeScryfallFetch` per Vitest).
- Import Archidekt (C-06): il browser non può chiamarla (CORS solo per localhost:3000), quindi sempre via Action `import` (`data-actions/src/import.js`, bundle `engine/import.mjs`, workflow `import.yml` su `requests/**`). L'Action scarica solo se l'autore del commit è membro e scrive l'esito nella richiesta (`status`, `deckName`, `result` come testo con sezioni "Commander/Deck/Sideboard", le intestazioni che conosce `parseDeckText`). L'app legge con `getImportRequest`. Nessun token a Archidekt. Richiesta `archidekt-user` (C-06b): `url` = nome utente, esito `decks` (solo mazzi pubblici); l'import multiplo (`import-decks.js`) salva un mazzo solo se ha comandante e carte tutte trovate, uno alla volta.
- `npm run dev` gira in modalità Vite `live` (`__ARCHIDEKT_LIVE__`): in demo gli import da Archidekt sono veri, tramite il ponte `/archidekt-api` del server di sviluppo (CORS); logica condivisa con l'Action in `web/src/domain/archidekt-import.js`. `dev:fake-github` esegue l'Action `import` vera. I test usano sempre risposte finte e un server proprio sulla porta 5174 (`dev:test`), così non si mescolano con `npm run dev` (5173). Il nome del mazzo importato è quello di Archidekt.
- Sottoagenti di test: non devono usare comandi `git` né scrivere log nella radice del repository (un `git checkout` ha già cancellato modifiche non committate); dirlo nel prompt.
- Scryfall `/cards/collection` (verificato sull'API vera) non riconosce il nome completo delle carte a più facce ("A // B"): si cerca per prima faccia e si abbina ignorando accenti e apostrofi; "A-Nome" (Alchemy) si cerca come "Nome". La finta dei test imita questi comportamenti.
- Sito pubblicato (C-16): workflow `.github/workflows/pages.yml` (test, build, Pages) su ogni push in `main`. `VITE_PUBLIC_SITE=true` (solo lì) dà l'ambiente `signed-out`: senza token si vede solo la pagina Accesso (`App.vue`), mai la demo; `dev` e `preview` restano demo. Il test `preview.spec.js` fa una seconda build in `web/dist-public` (porta 4174).
- Repository dati reale: pubblicare solo i file cambiati, mai `config/` (ha membri veri); `npm run build:data-repo:live` prepara il pacchetto con il proprietario come admin. Commit sul repository via `gh api` con script Node (`jq` non c'è sul PC).
- Banner «in aggiornamento»: `GitHubProvider` segna `pendingKind` (`deck|game|vote|config|initial`) solo per scritture in `decks/ games/ votes/ config/`; le richieste di import non lo accendono.
- Mazzo appena salvato (C-06e): `useDataStore.optimisticDecks` (riempito da `write('saveDeck')`) è unito allo snapshot da `snapshotWithPending` con `optimistic: true`; `DecksView` mostra «In aggiornamento…». Si svuota quando lo snapshot ha il mazzo o `pending` è falso. `GitHubProvider` controlla ogni `fastPollMs` (5 s) invece di `pollMs` (30 s) mentre un ricalcolo è in attesa. Nei test del provider `saveDeck` richiede `colorIdentity`.
- Wizard di autovalutazione (C-07): si apre al tocco su «Avanti: autovalutazione», prima di scrivere il mazzo (`saveDeckVersion` aggiunge sempre una versione). Rilevatori in `web/src/domain/deck-features.js`; combo da `web/src/platform/spellbook.js` (unico punto che parla con Commander Spellbook; dal browser funziona SOLO da localhost (sul sito pubblicato Spellbook non manda il permesso CORS), risolto con C-07c: richiesta `spellbook` in `requests/` eseguita dall’Action `import` (esito `combos`), il wizard aspetta circa 1 minuto; in demo locale il MockProvider chiama Spellbook direttamente; `null` se non risponde e le combo si dichiarano a mano). Combo valida = qualsiasi combo (anche a 3+ carte) che produce «Infinite…» o «Win the game»; valore di mana = somma dei cmc di Scryfall di tutti i pezzi (≥7 tardiva F3, ≤6 rapida F4). Finte: `tests/fixtures/spellbook-fake.js` (`mockSpellbook`). Dati passati al provider sempre come copie semplici (structuredClone non regge i proxy di Vue). Playwright non vede `<option disabled>` con `toBeDisabled`: usare l’attributo.
- Wizard nell’import da nome utente (C-07b, parte 1): `prepareDeck` (scarica, cerca carte e combo; esiti `ready|review|failed`) e `buildPreparedDeck` in `web/src/domain/import-decks.js`; `ImportArchidektUser.vue` prepara i mazzi uno dopo l’altro in sottofondo e apre il wizard del primo pronto (`DeckWizard` con `back-label` «Salta questo mazzo»). Due richieste all’Action per mazzo (Archidekt + Spellbook): circa 2 minuti a mazzo. L’elenco non ha più la fascia per riga: si sceglie nel wizard. Aiuti comuni in `deck-features.js` (`wizardInput`, `findDeckCombos`).
- Ricontrollo dopo l’aggiornamento da Archidekt (C-07b, parte 2): `planRecheck` (`deck-resync.js`) confronta game changer, combo e carte sospette _nuove_ con la versione salvata; se cambia qualcosa, o se Spellbook non risponde, o se la versione non ha `floor`, si apre `DeckWizard` dentro `AppModal` (`overlay=recheck-<id>`, «Annulla l’aggiornamento» = chiudere), altrimenti si salva da solo. `withAssessment` porta `floor`/`combos`/`flags` nella nuova versione (senza, il motore leggerebbe F1). Dati in attesa tenuti in `shallowRef`: il provider usa structuredClone e non regge i proxy profondi di Vue.
- Archidekt, categorie (C-06h/fix): una carta può avere più categorie e conta la **principale** (la prima dell’array `categories`, quella con la stella): `[Blink, Maybeboard]` = nel mazzo, `[Maybeboard, Blink]` = fuori (Sideboard). Prima si guardava «una qualsiasi» categoria fuori dal mazzo e le carte venivano scartate per errore (`archidektToText` in `web/src/domain/archidekt-import.js`). Strumenti a mano su servizi veri, mai nei test: `npm run live:diagnose -- <link Archidekt> [carte]` (sola lettura, usa `gh`) e `npm run test:live` (Playwright sul sito vero, solo con `LIVE_TOKEN` nel terminale, si ferma su «Annulla»; `tests/live` è escluso da Vitest e da `test:e2e`).
- Pagina Mazzi (C-08d): `groupDecksByOwner`/`filterGroups` in `web/src/domain/deck-groups.js`; una sezione per giocatore (la mia in cima, aperta, con etichetta «Tu»; le altre chiuse), menu «Mostra» (`data-testid="deck-filter"`), «Apri tutti/Chiudi tutti». I gruppi chiusi non montano le schede: nei test aprire con `expand-all` prima di contare i `.deck`. Nomi dei giocatori da `data.members` (`loadMembers`), ripiego sul login.
- Scheda mazzo (C-08): rotta `/mazzi/:id` (`DeckDetailView.vue`); calcoli in `web/src/domain/deck-stats.js` (storico fasce da `snapshot.events`, avversari da `games`); grafici in SVG fatto a mano (`TierStepChart`, `WinTypeDonut`), con alternativa testuale. Game changer e combo si leggono da `getDeck` (ultima versione), non dallo snapshot. Nei test il demo non ha storico: si inietta nello store Pinia (`addHistory` in `deck-detail.spec.js`). Per gli screenshot si apre la scheda dal link dell'elenco (gli id demo non si indovinano).
- Immagini e dati delle carte (C-08b): l'indirizzo dell'immagine si ricava dall'id Scryfall (`platform/card-images.js`, `small`/`normal`), senza chiamare l'API; il browser le tiene in cache e `CardImage.vue` le carica lazy. cmc/tipo/colori NON si salvano nei mazzi: `platform/card-cache.js` li legge da Scryfall (`/cards/collection` per id o per nome) e li tiene in IndexedDB 7 giorni (ripiego su memoria). Il demo non ha id Scryfall nei mazzi: i test li iniettano (`withCommanderCard`).
- Carte del mazzo (C-08c): `DeckCardsView.vue` legge costo/tipo/colori da `sharedCardCache().byIds` (non dal mazzo) e li unisce con `detailCards`; le pile esistono solo da 768px (`platform/viewport.js`, sul telefono si usa la lista); `<select>` e `<input>` a 44px, niente caselle da 24px (il controllo tocco automatico le boccia). Zone che scorrono di lato (`.piles`) vanno rese focalizzabili (`tabindex="0"`, `role="region"`, etichetta). Nei test, dati carte per id con `mockCards` (deck-cards.spec.js); gli agenti di test non devono scrivere log nella radice (ne erano finiti diversi).
- Dettaglio carta (C-08f): una sola `AppModal` (`name="card"`) in `DeckCardsView`; la carta scelta sta in `selectedName` e se si arriva con `?overlay=card` senza scelta la finestra si richiude. Ogni carta nelle viste è un `<button class="hit">` (le strisce delle pile sono alte 44px). Il corpo di `AppModal` ha `tabindex="0"` (regola axe `scrollable-region-focusable`). Gli screenshot dei test non vanno mai scritti a mano: se un file pesa pochi byte è un segnaposto, non una cattura. Le cartelle `review-screenshots/` non devono contenere script (Vitest li raccoglie).
- Statistiche mazzo (C-08g): calcoli puri in `domain/deck-metrics.js` (curva delle sole magie, 8 = «8 o più»; multicolore conta in tutti i suoi colori; simboli ibridi in entrambi i colori; le carte senza dati non entrano nei conteggi ma contano nella taglia del mazzo; probabilità ipergeometrica con logaritmi dei fattoriali). I dati delle carte si leggono UNA volta in `useCardData` (dalla scheda) e si passano come props, per non fare due richieste uguali in parallelo. Un contenitore `display: grid` che ospita tabelle o form larghi ha bisogno di `grid-template-columns: minmax(0, 1fr)`, altrimenti la card si allarga oltre lo schermo senza che il controllo di overflow della pagina se ne accorga. Chiavi della cache carte versionate (`id2:`): se `CardInfo` cambia, alzare la versione.
- Saltiness (C-08h): il salt EDHREC viene da Archidekt (`oracleCard.salt`, copre ogni carta; il JSON pubblico di EDHREC dà solo le 100 più salate) ed è un dato del **mazzo** (`deck.salt`, nome carta → numero), non della versione, così si aggiorna senza creare versioni; il comandante è tra le carte. Mazzi da testo non hanno salt (la scheda lo spiega). `planResync` lo tratta come cambiamento del mazzo (`version: null`). Fuori dal motore (voce C-08i, solo proposta). La richiesta `import` porta `salt`: l'Action pubblicata nel repository dati va aggiornata a mano (`engine/import.mjs`). Numeri nelle statistiche con la virgola: `it.deckStats.decimal`.
- Salvataggi dopo un aggiornamento (C-08h, bug): `DeckResync.commit` ricopiava a mano solo alcuni campi e perdeva il salt. Ora il mazzo da salvare si costruisce in `resyncedDeck` (deck-resync.js): ogni campo nuovo che un aggiornamento deve portare va aggiunto lì e testato. Test di contratto dei provider: il salt si salva e si rilegge. Controllare sempre sul repository dati vero (`gh api …/contents/decks/<id>.json`) che il campo sia stato scritto, non solo che l'Action risponda.
- Tag dei mazzi (C-08e): `deck.tags` (max 8, ognuno max 24 caratteri, doppioni senza badare alle maiuscole) è un dato del **mazzo**, non della versione; li modificano proprietario e admin da `DeckTags.vue` con `saveDeck` (rilegge il mazzo intero e riscrive solo i tag). Lo snapshot vero viene da `derived/snapshot.json`: l'Action `recalc` deve copiare `tags` (fatto nel codice, da pubblicare a mano nel repository dati). Con un tag attivo la pagina Mazzi apre tutti i gruppi.
- Lobby (C-09): il tavolo si compone solo nel modulo (stato locale); «Inizia» scrive UNA partita già `in_corso` con `startedAt` (non esiste una partita `lobby` salvata). Formati offerti: ffa4/ffa3/ffa56/1v1 (`lobbyFormats`, `web/src/domain/lobby.js`); i giocatori sono ordinati in cerchio dal primo (posto 1). La pagina mostra il promemoria se `activeGameOf` trova una partita aperta dell'utente. Nel modulo i `v-model` non vanno su chiamate di funzione: usare `:value` + `@change`.
- Fascia del tavolo (C-09): in lobby si sceglie la fascia (F1–F5, campo `tableTier` della partita) e ogni giocatore può usare solo mazzi di **quella** fascia, né più bassa né più alta (`decksForTier`/`lobbyProblems` in `lobby.js`; fascia del mazzo = `tier.current`, altrimenti `declaredTier`). Il catalogo delle modalità sta in `lobby-catalog.js`: tutto inibito («in arrivo») tranne ffa3/ffa4 e Commander finché il motore non le calcola. Nei test Playwright il demo ha un mazzo per giocatore e di fasce diverse: `tests/e2e/lobby-helpers.js` aggiunge mazzi F2 nello store (`addF2Decks`); quei mazzi spariscono al primo cambio dello snapshot, perciò il promemoria ricorda i nomi già visti.
- Produzione di mana (C-08g, correzione): Scryfall dà `produced_mana` letterale (Arcane Signet, Command Tower… = tutti e 5 i colori). `colorBalance(cards, identity)` conta solo i colori dell'identità del mazzo (`deck.colorIdentity`); l'incolore conta sempre.
